Bare Metal Rust
a book for building your own OS

A chapter-by-chapter route from an empty Cargo project to a kernel that boots real (or virtual) hardware and hands you a playable terminal. No copy-paste kernels — theory, sequencing, and the primary sources, so you write every line yourself.

15 chapters x86_64 target QEMU-first, real hardware later no_std Rust
Preface

Is a terminal game actually the right target?

Short answer: yes, keep it — but let me argue it properly instead of just agreeing with you.

An OS project dies from scope, not difficulty. The useful trick is to pick an end goal that forces you through the same core subsystems a "real" OS needs, without dragging in a second whole discipline. A terminal game sitting directly on your kernel needs exactly four things that every teaching OS needs anyway: something on screen, a clock, a keyboard, and memory you control. That's VGA output, the timer interrupt, keyboard interrupts, and paging/heap. You get a satisfying, demoable result the moment those four exist — which is exactly when most solo OS projects lose momentum, so finishing there matters.

"Being able to download shit" means a network stack: a NIC driver, an Ethernet/ARP layer, IP, and TCP or UDP, all before you can even resolve a hostname — and that's before touching a filesystem to save what you downloaded. Each of those is roughly its own mini-project, and several depend on hardware quirks (which virtual or real NIC you're targeting) that add debugging pain unrelated to OS theory. It's a fantastic next project, not a better first one.

Recommendation Ship the terminal game as the v1 milestone (chapters 1–12). Chapter 13 then surveys the next mountains — filesystems, networking, multitasking, a userspace/syscall boundary — so you can pick your v2 goal with open eyes instead of guessing at the effort involved.
Chapter 1

Mental model & prerequisites

Before any code, get the shape of the machine straight in your head. A CPU boots into a legacy 16-bit mode, gets promoted through 32-bit protected mode, and (on x86_64) ends in 64-bit long mode — each stage unlocking capabilities the last one didn't have. Your kernel is just a program the firmware jumps to; there is no libc, no heap, no threads, no std underneath you until you build them yourself.

What you should already know

  • Comfortable, non-beginner Rust: ownership, traits, generics, and — importantly — unsafe, because talking to hardware is inherently unsafe.
  • Basic C-level computer architecture: registers, the stack, pointers, endianness.
  • Command-line comfort: you'll be scripting builds, not clicking buttons.

Concepts to read up on now

Background reading
  • Kernel (operating system) — what a kernel actually owns vs. delegates.
  • Protection ring — why "kernel mode" exists at all.
  • x86-64 — the architecture you'll target first (widest emulator/tooling support).
  • Long mode — the 64-bit operating mode your kernel will actually run in.
Tip Target x86_64 first, not ARM or RISC-V. The tooling, docs, and QEMU support are the deepest, and everything here assumes it.

Level up first: from "I know what it is" to "I've used it"

Knowing the definitions of ownership, traits, generics, unsafe, registers, the stack, and endianness isn't the same as having used them — and the OS is a rough place to learn several of them for the first time simultaneously. This is worth a few focused days before chapter 3.

Priority 1 — unsafe Rust This is the one that actually gates you: almost all hardware-facing kernel code lives inside unsafe blocks. Reading about it isn't enough; build something with raw pointers so aliasing rules and manual memory ownership stop being theoretical. The classic exercise is working through "Learning Rust With Entirely Too Many Linked Lists" — do at least the first two or three list variants before starting the OS.
Priority 2 — bit manipulation Registers, page table entries, the PIC, and the IDT are all "set these 3 bits, clear that one, read this range out." Practice until it's boring: write a function that sets/clears/toggles/reads an arbitrary bit in a u32, hand-build a bitfield struct (a few flags packed into one integer) without a crate, and get comfortable converting small numbers between hex, binary, and decimal in your head.
Priority 3 — pointers & endianness, made concrete Do this once, physically: take a u32, call .to_le_bytes() and .to_be_bytes() on it, and work out by hand why the byte orders differ. Then cast a raw pointer to a different type and read through it — e.g. walk a *const u32 one byte at a time via a *const u8. That single exercise demystifies most of what's confusing about memory-mapped registers later.
Priority 4 — stack & registers, just enough You don't need assembly fluency, but you should recognize a stack frame, a return address, and a calling convention concretely, not abstractly. If you want one source, the chapter on machine-level program representation in Computer Systems: A Programmer's Perspective (CS:APP) is the standard reference and covers x86 registers and the stack directly — you only need that one chapter, not the whole book.
Priority 5 — traits & generics, one real rep You're closest here already. Implement a trait yourself instead of just using one — give a custom struct a Display impl, or write your own trait with a default method, plus one generic function with a trait bound. That's genuinely enough; Chapter 5's core::fmt::Write implementation will feel familiar instead of new.
Background reading & exercises
  • Learning Rust With Entirely Too Many Linked Lists — the standard hands-on route into raw pointers and unsafe.
  • The Rustonomicon — pair with the exercise above rather than reading it cold.
  • Endianness
  • Bit field
  • Call stack and calling convention
  • Processor register
  • Computer Systems: A Programmer's Perspective — the "machine-level representation of programs" chapter specifically, for stack/register grounding.
Chapter 2

Toolchain & targets

Your kernel isn't compiled "for your computer" the normal way — it's cross-compiled for a bare target triple with no operating system underneath it at all. Rust's nightly channel is required here because the features that make this possible (custom targets, certain build-std flags) aren't stabilized.

You'll define your own target specification describing the CPU, the calling convention, and — critically — that there is no OS to link against. You'll also need rust-src so Cargo can rebuild Rust's own core library for that custom target, since the prebuilt one assumes a host OS exists.

Decisions to make in this chapter

  1. Install and pin a nightly toolchain for this project specifically, not globally.
  2. Decide on a custom JSON target spec vs. one of Rust's built-in bare-metal targets — research both before choosing.
  3. Set up a build script or Cargo config so a plain cargo build "just works" for contributors (including future-you).
Background reading
  • rustc: custom targets
  • Cargo unstable: build-std
  • Cross compiler
Trap Nightly Rust moves fast; a target-spec field that works today may be renamed next month. Pin an exact nightly date in rust-toolchain.toml so your build doesn't randomly break.
Chapter 3

The freestanding binary

A normal Rust binary quietly depends on an OS to set up its stack, hand it argv, and catch its panics. Stripping that away is the actual meaning of "freestanding": no standard library, no runtime, no entry point handed to you by the OS loader. You provide the entry point, and you provide the panic behavior, because there's no OS underneath to provide either.

What "freestanding" removes, concretely

  • The standard library — you're left with core (and later, hand-rolled alloc support once you have a heap).
  • The normal main entry point and the C runtime that calls it.
  • Unwinding-based panics — you'll choose an abort strategy instead.
  • Anything that assumes a filesystem, threads, or process model exists.

This is also where you'll write your first genuinely OS-flavored piece of code: a panic handler. It doesn't need to do much yet — print something and halt — but every kernel has one, because core requires it by contract.

Background reading
  • Freestanding / embedded software model
  • The Rustonomicon — your reference for everything unsafe from here on.
  • Rust reference: the entry point
Chapter 4

Booting the kernel

Firmware doesn't know your kernel exists; it looks for a bootable disk, loads a small program, and jumps to it. That program — the bootloader — is responsible for getting the CPU from its ancient legacy startup mode into a mode your Rust code can actually run in, and for handing your kernel some basic information about the machine (memory map, framebuffer, etc.).

You have a real decision here: write your own minimal bootloader (excellent for understanding BIOS/UEFI handoff, real-mode-to-long-mode transitions, and the Multiboot-style boot protocols) or use an existing Rust bootloader crate and focus your effort on the kernel itself. Neither is "cheating" — they teach different things.

ApproachYou learnCost
Own bootloaderReal→protected→long mode transitions, GDT setup, disk/firmware handoffSlow start, more assembly-adjacent work
Bootloader crate + MultibootKernel design, gets to interrupts/memory fasterLess firmware-level understanding
Tip If your priority is the terminal game, use an existing bootloader and spend your learning budget on chapters 6–12. Come back and write your own bootloader as a dedicated side quest later — it's a great standalone project.

  • Multiboot Specification

  • OSDev Wiki — the single best community reference for every step in this chapter
Chapter 5

VGA text output — your first "hello"

Long before you have a windowing system, you have a rectangle of characters mapped directly into memory: write a byte to the right address and a character appears on screen. This is the VGA text buffer — a legacy but wonderfully simple way to get your first visible proof of life, and it's exactly the display mode your terminal game will render into.

The interesting design work here is wrapping that raw memory-mapped buffer safely: tracking a cursor position, handling scrolling when the screen fills, and exposing something that feels like print!/println! to the rest of your kernel via Rust's core::fmt::Write trait.

// shape, not implementation — the trait you're aiming to satisfy impl core::fmt::Write for Writer { fn write_str(&mut self, s: &str) -> core::fmt::Result { ... } }
Background reading
  • VGA text mode
  • Memory-mapped I/O
  • core::fmt::Write
Trap Writes to the VGA buffer are volatile — the compiler doesn't know a memory-mapped device is watching, so it's free to reorder or eliminate writes it thinks are "dead." Look into volatile access before you spend an hour debugging text that mysteriously doesn't appear.
Chapter 6

CPU exceptions & the GDT

Before you can safely handle interrupts, you need two pieces of CPU bookkeeping in place. The Global Descriptor Table describes memory segments and privilege levels to the CPU — mostly a legacy holdover in long mode, but you still need a minimal one, plus a separate stack (via the Interrupt Stack Table) reserved for catastrophic faults so a stack overflow doesn't corrupt itself while trying to report a stack overflow.

Then come CPU exceptions: faults the processor raises itself — divide-by-zero, invalid opcode, page fault, the infamous double fault. Handling these correctly, especially the double fault, is what turns "kernel triple-faults and the VM silently reboots" into "kernel prints a readable panic and halts," which will save you enormous debugging time in every later chapter.

Background reading
  • Global Descriptor Table
  • Interrupt Descriptor Table
  • Double fault
  • Page fault
Tip Get double-fault handling and a dedicated fault stack working before you write any interrupt handlers. It's the difference between a stack trace and a silent QEMU reboot loop.
Chapter 7

Interrupts & the timer

Hardware interrupts are how the outside world — a timer chip ticking, a key being pressed — gets the CPU's attention without you polling in a busy loop. You'll configure the legacy Programmable Interrupt Controller (or the more modern APIC) to route these signals to entries in your IDT, and you'll need to explicitly tell the controller "I've handled this one" at the end of each handler, or it will stop delivering further interrupts.

The timer interrupt in particular is worth building carefully: it's your kernel's heartbeat. Every "tick"-based thing later — task switching, the game's frame timing, anything time-based — hangs off this single interrupt firing at a steady rate.

Background reading
  • Interrupt (general concept)
  • Programmable Interrupt Controller (PIC)
  • Advanced PIC (APIC)
  • Programmable Interval Timer
Trap Forgetting to remap the legacy PIC moves its interrupt numbers so they collide with CPU exception numbers — a keyboard press can look identical to a CPU fault to your handler table. This bites almost everyone once.
Chapter 8

Keyboard input

With interrupts working, the keyboard is "just" another interrupt source, but a fiddly one: the controller hands you raw scancodes, not characters, and depending on the scancode set you may get one byte per key or a short multi-byte sequence for special keys. You'll build a small state machine to turn scancodes into logical key events, then a layer on top to turn key-down events into actual characters (accounting for shift, at minimum).

This is also your first real lesson in interrupt-safe data sharing: the interrupt handler fires asynchronously and needs to hand key events to the rest of your kernel without a heap, without threads, and without deadlocking against itself.

Background reading
  • Scancode
  • PS/2 port
  • Ring buffer — a natural fit for an interrupt-fed input queue
Tip Keep the interrupt handler itself tiny — decode just enough to push a raw event into a queue, and do all the interesting logic (key-to-character mapping, game input handling) outside the interrupt context. Long-running interrupt handlers cause missed or delayed interrupts elsewhere.
Chapter 9

Memory I — paging & virtual memory

Every address your kernel touches so far has been a physical address by luck, not by design. Real memory management means virtual memory: the CPU translates every address through page tables before touching physical RAM, which is what makes memory protection, and later, per-process isolation, possible at all.

Your bootloader (chapter 4) likely already set up an initial page table to get you into long mode; this chapter is about understanding that structure well enough to walk it, map new pages deliberately, and eventually manage physical frames yourself instead of relying entirely on what the bootloader handed you.

Background reading
  • Memory paging
  • Virtual memory
  • Page table (multi-level structure on x86_64)
  • Translation lookaside buffer — why you must flush it after remapping
Trap Page faults after a mapping change are almost always a forgotten TLB flush, not a logic bug in the mapping code itself. Rule that out first.
Chapter 10

Memory II — the heap

With paging understood, you can carve out a fixed region of virtual memory and back it with real frames, then install an allocator over that region so alloc::vec::Vec, String, and friends become usable — a genuinely nice milestone, since a huge amount of "normal" Rust suddenly works again.

The interesting design decision is which allocator strategy to implement: a simple bump allocator (fast, can't reclaim individual frees), a linked-list free-list allocator (reclaims memory, more bookkeeping), or a fixed-size-block allocator (fast reclaiming for common small sizes). Each is a legitimate, well-documented tradeoff — pick based on what you want to learn, not on which is "best."

Background reading
  • Memory management (general strategies)
  • Free list
  • alloc crate docs — what unlocks once your allocator exists
  • GlobalAlloc trait — the interface your allocator must implement
Chapter 11

The terminal shell

This is where the pieces from chapters 5–10 assemble into something that feels like an OS instead of a pile of subsystems: a loop that reads keyboard events, echoes characters to the VGA buffer with a blinking cursor, supports backspace and a scrolling history, and dispatches a typed line to a command handler.

Treat this like designing a tiny language: a command is a name plus arguments, parsed from one line of text, dispatched to a Rust function. Build a couple of trivial commands first (echo, clear, help) to prove the loop, before your game becomes just another command this shell can launch.

Background reading
  • Shell (computing)
  • Read–eval–print loop — the general pattern your shell follows
  • Command-line interface
Tip Design commands as a trait or a function-pointer table from day one, even with only two commands. Retrofitting a dispatch system once you have a shell full of copy-pasted if chains is a chore you can skip entirely.
Chapter 12

Turning it into a game

A game loop needs three things your kernel now has: a way to draw, a way to read input, and a way to measure time — the timer interrupt from chapter 7. Rather than a busy-spin loop, drive updates off your timer tick count so the game's speed doesn't depend on how fast the underlying hardware happens to run.

Two OS-specific wrinkles worth planning for: you have no OS-provided randomness source, so you'll need a small pseudo-random number generator seeded from something that varies (the timer tick count at boot is a common, if weak, choice); and you have no double-buffered framebuffer in text mode, so redraw carefully — clear-and-redraw-every-frame will visibly flicker, while only overwriting changed cells will not.

Background reading
  • Game loop
  • Pseudorandom number generator — look at simple ones like xorshift or an LCG, not cryptographic ones
  • Multiple buffering — the general idea behind flicker-free redraws
Tip Snake, a maze-runner, or a falling-blocks game are the classic choices here for good reason: fixed-size grid, discrete tick-based movement, tiny state. All three map cleanly onto "redraw only the changed cells" without needing real graphics.
Chapter 13

Beyond the terminal — where the next mountains are

Once the game runs, you've built the load-bearing parts of a real kernel: boot, interrupts, memory, and a basic run loop. Everything past this point is optional, and each item below is genuinely its own project — pick the one that matches what you want to learn next, rather than trying to do all of them at once.

DirectionWhat it addsRoughly how big
MultitaskingA scheduler, context switching, cooperative or preemptive tasksMedium — mostly builds on what you already have
FilesystemA disk driver, a filesystem format (even a toy one), persistent storageMedium–large — new hardware layer (disk I/O)
Networking ("download shit")NIC driver, Ethernet/ARP, IP, TCP/UDP, possibly DNSLarge — several independent layers, hardware-specific driver work

Chapter 14

Tips & traps, collected

  • QEMU first, real hardware second. A crash in QEMU gives you logs and a debugger; a crash on real hardware gives you a black screen. Only test on real metal once things are stable.
  • Build a serial-port logger early. Once VGA text is up, redirect debug output to the serial port too — QEMU can pipe that straight to your terminal, which is far easier to read than screenshots of a VM window.
  • Triple faults are usually "handler chain not set up yet," not exotic bugs. If QEMU silently reboots, suspect a missing or misconfigured IDT/GDT entry before anything else.
  • Commit at every working milestone. Kernel bugs can corrupt state in ways that are hard to bisect; a granular git history is more valuable here than in ordinary application code.
  • Read a real kernel's source once you're past chapter 8. Doing so earlier is overwhelming; doing so later helps you recognize why a design decision you made works or doesn't.
  • Keep interrupt handlers short and non-blocking. Anything slow belongs in code the handler merely triggers, not in the handler itself.
  • Expect the double fault handler to save you constantly. Don't treat chapter 6 as optional groundwork — it's the tool you'll use to debug every later chapter.
